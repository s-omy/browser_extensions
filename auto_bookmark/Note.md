# 開発ノート

仕様・構成・データモデルは [Readme.md](Readme.md)、使い方は [user_guide.html](user_guide.html) を参照してください。
このファイルは、開発の経緯と、遭遇した問題・対応・未解決の課題の記録です。

## 1. 開発の流れ

```
Phase 1: 思想の確立
  サードパーティ製拡張機能のロギング・送信リスクを避けるため、完全ローカルの自作を決定
    ↓
Phase 2: 疎通と基礎設計
  Python での HTML パース・Gemini API（gemini-3.6-flash）によるフォルダ Description 自動生成に成功
    ↓
Phase 3: ブラウザ拡張への移植
  Manifest V3 準拠の Chrome 拡張化。コンテキストメニュー・設定画面・ローカルストレージ連携
    ↓
Phase 4: UI/UX の高度化
  Unified/Split の Diff プレビュー、アコーディオン、進捗率（%）表示
    ↓
Phase 5: 堅牢化とセーフティ突破
  フォルダ単位のチャンク化、セーフティ誤判定を避けるための「プロンプトの抽象表現化」
    ↓
Phase 6: レビュー対応（2026-09）
  失敗を成功に見せない、保護フォルダの実装、ID による同定、課金の制御、
  API 呼び出しの共通化、権限の縮小、モジュール分割、ドキュメントの全面改訂、自動テストの追加
    ↓
Phase 7: マルチプロバイダ対応（2026-09-23）
  Gemini 直呼び出しをやめ、gemini.js を「callGemini オーケストレーション + Geminiアダプター」に、
  openai-compatible.js を新設して LiteLLM Proxy 等の OpenAI 互換エンドポイントに対応。
  呼び出し側（ai-tasks.js 以降）はプロバイダを一切意識しない設計に
```

### 時系列

1. **既存拡張機能の精査と自作への舵切り**
   既存ツール（サードパーティ製のブックマーク整理拡張）が、性能改善の名目でウェブ履歴などを記録・送信するリスクを指摘。トークン・プロンプト・キャッシュ・コンテキストを自分で管理するため、公式 Gemini API を直接呼ぶ完全ローカルのツールとして設計を開始した。
2. **ローカル Python スクリプトによる疎通確認**
   モデルを gemini-3.6-flash に固定。Chrome エクスポート形式の HTML ブックマークをパースし、フォルダ配下のエントリからフォルダの Description を Pydantic（Structured Outputs）で構造化抽出するプロンプトを検証し、成功した。
3. **Manifest V3 への移植とアーキテクチャ構築**
   Python のパースロジックを拡張機能へ移植。右クリックから「ページ情報」と、ストレージに蓄積した「フォルダ記述」を Gemini に渡して自動格納する基盤を作った。
4. **セーフティフィルター（PROHIBITED_CONTENT）と性能の壁**
   ブックマーク内の刺激的なタイトルで、API が PROHIBITED_CONTENT（セーフティブロック）を起こした。1件ずつの同期は遅く、全件一括送信は容量が膨らんで遮断された。
5. **データクレンジングとチャンク処理の確立**
   実処理の前にタイトルを無毒化（クレンジング）する方式を導入。生の違反例を含まない抽象的な指示プロンプトにした。処理単位は 50 件 → フォルダ単位 → 現在はフォルダ内 30 件ずつのチャンクへと細かくし、各応答の `finishReason` を検査してブロックを検知する形にした。
6. **多次元メタデータの統合とダッシュボードの完成**
   階層パス、QuickAccess（ブックマークバー配下）、Untouchable（保護。親から継承）の属性を実装。ページコンテキストにフォルダ情報を統合し、自然順ソートのアコーディオンとタグ UI を持つ一覧を構築した。
7. **プログレスバーと進捗の見える化**
   `type: "progress"` の通知と、設定画面の重い処理の進捗率（%）表示を追加した。
8. **レビュー対応（Phase 6）**
   コードレビューで、ドキュメントに書かれた機能が実装と食い違っている箇所（特に保護フォルダ）や、失敗を成功と誤認させる表示、想定外の課金の発生点が見つかった。§3 に対応の要約を残す。
9. **マルチプロバイダ対応（Phase 7）**
   「使う LLM は人によって違う。LiteLLM のような Proxy に差し替えられるか」という要望を受けて設計を検討。B/C/D 対応（Phase 6）の時点で、AI 呼び出しの実処理が `gemini.js` の中にだけ閉じていた（呼び出し側は `callGemini`/`GeminiError` しか触らない）ため、想定より小さな変更で対応できた。§5 に詳細を残す。

## 2. 発生した問題と対応内容

開発中に直面した、ブラウザ拡張機能特有の制限と Gemini API の仕様に関する記録です。

### ① インラインスクリプトの CSP 違反
- **問題**: `options.html` に直接書いた `<script>` が、Manifest V3 の CSP によりブロックされた。
- **対応**: ロジックを外部ファイルに分離し、`<script src>` で読み込む標準的な構成にした。現在は `<script type="module">` で ES モジュールとして読み込んでいる。

### ② fetch のドメイン・パス結合エラー
- **問題**: `background.js` で、ホスト名のスペルミスと、リクエストパス（`/v1beta/models/...`）の脱落により `TypeError: Failed to fetch` が発生した。
- **対応**: エンドポイントを一元管理した。現在は `gemini.js` の 1 か所にだけ存在する。

### ③ 外部サイト・タブからの実行時の Scripting アクセス拒否
- **問題**: `host_permissions` が API ドメインだけだった初期に、外部サイト上で `executeScript` による meta タグの抽出が拒否された。また、タブバーで右クリックした場合は、DOM に触れずエラーになった。
- **経緯**: 当初は `"<all_urls>"` を付与して開通させ、DOM に触れない場合は `try/catch` で「タイトルと URL だけ」のフォールバックにした。
- **現在**: `<all_urls>` と `tabs` 権限を廃止し、`activeTab`（メニュー・アイコン・ショートカットの操作を行ったタブにだけ一時的に付与）と `scripting` の組み合わせにした。権限の警告が小さくなり、ストア審査やユーザーの信頼に有利になる。タブ右クリックで `activeTab` が付与されるかは実機での確認が残っており（§4）、付与されない場合は従来どおり「タイトルと URL のみ」に縮退する。

### ④ チャット画面の Markdown レンダラーとの干渉（当時の開発環境の事情）
- **問題**: AI とのやり取りでソースコードを出力すると、生の HTML 閉じタグや絵文字が描画エンジンに誤認され、コードブロックが崩れた。
- **当時の対応**: 生 HTML と生絵文字を避け、`String.fromCodePoint(10134)` のように数値から生成した。
- **現在**: これは製品コードの可読性を落とすため、記号は `ui-common.js` の `ICONS` 定数に、ソース上の絵文字としてまとめた（DOM は `h()` ヘルパーで構築し、HTML 文字列は使わない）。

### ⑤ 大量データの一括送信・特定ワード集中によるセーフティ遮断
- **問題**: 全タイトルを 1 リクエストにまとめて送ると、容量の過密や、特定フォルダへのセンシティブな語の集中で、リクエスト全体が PROHIBITED_CONTENT として遮断された。
- **対応の変遷**: 全体を丸投げする方式をやめ、フォルダ単位のチャンクに分けた。プロンプトの違反例の生文字を排除し、ブロックを検知したチャンクだけを「判定不能（現状維持）」として、他の処理を継続する。
- **その後の見直し**: 当初の「フォルダ単位・最大 30 件」では、31 件目以降が黙って対象外になっていたため、フォルダ内を 30 件ずつのチャンクに分割する形に改めた。①フォルダ解析も、全フォルダを 1 リクエストに詰めていたため、8 フォルダずつのバッチにした。ブロック・出力途切れ時は対象を二分割して再試行し、原因の項目だけを切り分ける（`processWithBisect`）。

## 4. 未解決の課題・制限事項

1. **実機での確認が未了の点**: 開発中の検証は、`chrome.*` と `fetch` をモックしたページで行った。次の点は実機の Chrome で確認が必要。
   - タブ右クリック（`tab` コンテキスト）で `activeTab` が付与されるか（付与されなくても縮退するが、ページの meta を使えなくなる）
   - 通知ボタンの表示（OS による）と、`storage.session` を使った「元に戻す」
   - ショートカットの既定キー `Alt+Shift+B` が競合しないか
   - Gemini の応答スキーマの `enum` に、フォルダ数の多いケースで上限がないか（超えた場合は「AI 判定に失敗」として未分類に入り、通知で分かる）
2. **ナレッジが推定であること**: Gemini の URL コンテキスト機能などでページ本文を取得すれば精度を上げられるが、構造化出力との併用可否とコストが未検証のため、採用していない。
3. **ブロックされ続ける URL**: ③で保存されないため、同期のたびに再試行される（1 件ずつの問い合わせ）。失敗した URL を記録して間隔を空ける仕組みが必要になる可能性がある。
4. **レート制限**: 429 はバックオフ付きリトライのみで、並列化や事前の速度制御はしていない。無料枠など RPM の厳しいキーでは、大きなフォルダ構成の②が遅くなる。呼び出し回数の見積もりは Readme §10。
5. **対象範囲**: ブックマークバー／その他のブックマーク直下に置かれたブックマーク自体は、①・②の対象外（システムフォルダ扱い）。
6. **取り消しは直前の 1 回のみ**。動作ログの書き込みは、サービスワーカーと設定画面が同時に書くとまれに 1 件欠ける。
7. **自動テストは `tests/` にある**（2026-09-23 追加）。Node.js を使わず、`chrome.*` と `fetch`（Gemini形式・OpenAI互換形式の両方）をモックしたブラウザページ（`tests/run.html`）から、実際の各モジュールを `import` して検証する。135件、全て成功を確認済み。実行方法は `tests/README.md`。カバーしていないのは、実 Chrome・実際の外部 API・見た目・OS 依存の挙動（§1の「実機での確認が未了の点」と同じ）。
8. **OpenAI 互換プロバイダは、拡張機能を通した実機検証はまだ**。ただし 2026-09-24 に、ユーザー環境（Ollama + LiteLLM Proxy + `qwen3:8b`、`ollama/<model>` 経由）に対して `curl` で疎通・スキーマ検証を実施し、次を確認できた。
   - 素のテキスト応答（接続テスト相当）: 成功。ただし Qwen3 の思考モードにより、短い応答でも `completion_tokens` が大きくなる（例: `"OK"` の2文字に対し151トークン）。
   - `response_format: json_schema` + `strict:true` を付けた場合: フラットオブジェクト（`categorizePage` 相当）・配列を含むネスト（`cleanseTitlesBulk` 相当）のどちらも、スキーマ通りの JSON で返り、`enum` 制約も守られた。**スキーマ付きのときは思考モードがほぼ発生せず、トークン数も少ない**（同条件で21〜38トークン）。実運用（①②③）はほぼ全てスキーマ付きの呼び出しのため、これは良い兆候。
   - クレンジング（安全な表現への言い換え）も、実際に機能的に妥当な出力になることを確認した。
   - 未確認: 拡張機能本体（`chrome.permissions.request()` を含む実際の保存フロー、大きなバッチでの実時間・タイムアウト耐性、429/レート制限時の挙動）。他のバックエンド（Anthropic 等を LiteLLM 経由で使う場合）や他モデルでの Structured Outputs 対応は未検証で、引き続きバックエンド依存の注意点として残る。

## 5. マルチプロバイダ対応（Phase 7）の詳細

- **設計判断**: 「Gemini + OpenAI互換の2系統をプロバイダアダプターとして切り替える」方式を採用（既存 Gemini ユーザーの挙動・設定を一切変えない代わりに、`gemini.js` に2つ目のレスポンス形式の分岐が増える）。もう一案の「OpenAI互換チャット補完APIに一本化し、Geminiも自社のOpenAI互換パスで呼ぶ」は、コードは単純になるが、既存の `gemini_key` 単体設定からの移行や、Gemini固有のブロック理由（`promptFeedback.blockReason`）の粒度が失われる点がデメリットとして見送った。
- **変更点**: `gemini.js` の `callGemini` は、素の Gemini リクエスト/レスポンス処理から「プロバイダアダプター（`buildRequest`/`parse`/`errorDetail`）を呼ぶオーケストレーター」に変わった。Gemini 自身のアダプターは `gemini.js` 内に残し、新規の `openai-compatible.js` が LiteLLM Proxy 等向けのアダプターを提供する。`ai-tasks.js` 以降のファイルは、`apiKey` という文字列を渡す代わりに `connection`（`{provider, apiKey, baseUrl, model}`。`storage.js` の `getLlmConnection()` が返す）を渡すよう、シグネチャだけを機械的に変更した。プロンプト・スキーマ・エラーハンドリングのロジックは変更していない。
- **スキーマの扱い**: `ai-tasks.js` には Gemini 方言（大文字の `type`、`response_schema`）のスキーマを1種類だけ書く。`openai-compatible.js` がこれを標準 JSON Schema（小文字 `type`、`additionalProperties:false`）へ変換し、OpenAI の Structured Outputs（`response_format: {type:"json_schema", strict:true}`）として送る。
- **権限**: 自前ホストの LiteLLM 等は任意のオリジンになりうるため、`manifest.json` に `optional_host_permissions: ["http://*/*","https://*/*"]` を宣言し、実際の許可は保存時に `chrome.permissions.request({origins:[<入力したオリジン>+"/*"]})` で1件だけ動的に求める形にした（`<all_urls>` を事前に要求しない）。
- **開発中に踏んだ落とし穴**: JSDoc コメント（`/** ... */`）の説明文に `chrome.*/fetch` と書いたところ、`*/` の並びでコメントが早期に閉じて構文エラーになった（`chrome.* と fetch` と書き直して解決）。また、テスト実行中にブラウザの HTTP キャッシュが古い `.js` を返し続け、ソースを直しても失敗が再現するという事象に遭遇した（`Cache-Control: no-store` を返す `tests/serve.py` を新設し、さらに疑わしいときはポート番号を変えて開き直すことで解決。詳細は `tests/README.md`）。
